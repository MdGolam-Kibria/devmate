# M2 — MCP Client

Status: **COMPLETED** (2026-10-10)

## Goal

DevMate's core MCP client: connect to MCP servers, run the `initialize` handshake, discover their tools dynamically,
register them, execute them with `tools/call`, and handle every failure (connection, timeout, invalid tool, invalid
arguments, server, session, transport). Done when `search_code("Kafka")` runs through it **without an LLM**.

## Architecture

Decisions and alternatives: [ADR-0004](../decisions/ADR-0004-mcp-client.md). All components wrap the official MCP
Java SDK 2.0.1. DevMate defines no protocol structures of its own.

```text
 /api/mcp (McpController)   folder Q&A (FolderAssistant)   agent (M3)
              └──────────────┬──────────────┘
                     McpClientService            facade; approved folders → MCP roots
                ┌────────────┴────────────┐
           ToolRegistry              ToolExecutor
   tools of all servers;          find → read-only? → args fit inputSchema? (SDK validator)
   tools/list per session or      → tools/call → McpToolResult / McpUnavailableException;
   list_changed; lower priority   log + timer devmate.mcp.client.calls, MDC mcpServer/toolName
   wins a name clash                     │
                └────────────┬────────────┘
                     McpConnection  (one per devmate.mcp.servers.<name>)
                     lazy open · drop on breakage · classify failures · retry read-only once
                     McpSession     initialize result (serverInfo, protocol, capabilities), listTools, callTool
                     McpTransport   SDK HttpClientStreamableHttpTransport (connect timeout, max-response-size)
                            │  Streamable HTTP
                     MCP servers: files (127.0.0.1:8091/mcp, priority 10), more by configuration
```

The lifecycle the brief asks for: **Connect** (`McpTransport`, `McpConnection`) → **Initialize** (`McpSession`) →
**Discover** (`tools/list` in `ToolRegistry`) → **Register** (unique names across servers) → **Execute**
(`ToolExecutor`) → **Receive result** (`McpToolResult`).

### Error handling

| Brief | Code | Where it comes from | Surfaces as |
|---|---|---|---|
| Connection failure | `CONNECTION_FAILED` | refused, unknown host, connect/initialize timeout, initialize rejected | thrown → API 503 |
| Timeout | `TIMEOUT` | no answer within `request-timeout` | `tools/call`: returned, 504, session kept, not retried; otherwise thrown |
| Invalid tool | `UNKNOWN_TOOL` | not in the registry, or the server says "Unknown tool" (its list is then re-read) | returned, 404 |
| Invalid arguments | `INVALID_ARGUMENTS` | DevMate's schema check before sending, or JSON-RPC -32602 | returned, 400 |
| Server errors | `SERVER_ERROR`, `TOOL_ERROR` | other JSON-RPC errors / the tool's own `isError` | returned, 502 / 200 |
| Session errors | `SESSION_ERROR` | server no longer knows the session (404) | new session + one retry (read-only), else thrown |
| Transport errors | `TRANSPORT_ERROR` | bad HTTP status, unreadable or oversized message | one retry if not oversized, then thrown → 503 |
| (policy) | `TOOL_NOT_ALLOWED` | tool not declared `readOnlyHint=true` | returned, 403, never sent |

A tool name nobody offers while some server is unreachable is reported as that server's outage, because the tool may
be there. Messages are safe to show: no arguments, no tool output, and at most one cleaned, bounded line of a server's
JSON-RPC error message.

## Delivered

- `dev.devmate.client.mcp`: `McpTransport`, `McpSession`, `McpConnection`, `ToolRegistry`, `ToolExecutor`,
  `McpClientService`, plus `McpClientProperties` (validated: http(s) only, no credentials/query in the URL, name
  pattern, positive timeouts, 1 KB–2 GB size cap), `McpErrorCode`, `McpServerStatus`, `McpRoots`,
  `McpClientConfiguration`. Replaces the folder slice's `McpToolClient` and `FilesMcpProperties`.
- Several servers by configuration (`devmate.mcp.servers.<name>`), with an explicit `priority` for tool-name clashes.
- Background discovery at startup (`devmate.mcp.connect-on-startup`), which only logs.
- `McpController`: `GET /api/mcp/servers`, `GET /api/mcp/tools[?refresh=true]`, `POST /api/mcp/tools/{name}/call`
  (JSON only: 415 for form/text posts).
- `web/HostHeaderFilter`: requests with a foreign `Host` get 403 (DNS rebinding; `DEVMATE_ALLOWED_HOSTS`).
- Folder Q&A moved onto `McpClientService`, with unchanged behaviour (`check-client.sh` 89/89).

Config:

```yaml
devmate.mcp:
  connect-on-startup: ${DEVMATE_MCP_CONNECT_ON_STARTUP:true}
  servers:
    files:
      url: ${DEVMATE_FILES_MCP_URL:http://127.0.0.1:8091/mcp}
      request-timeout: ${DEVMATE_FILES_MCP_TIMEOUT:30s}
      priority: 10
      # connect-timeout 3s, initialization-timeout 10s, max-response-size 4MB
```

## Run (the DoD, no LLM)

```bash
export JAVA_HOME=~/.jdks/ms-25.0.4.1 && ./mvnw -q package -DskipTests
DEVMATE_FILESYSTEM_ALLOWED_ROOTS=$HOME/projects java -jar devmate-files-mcp/target/devmate-files-mcp-*.jar &
java -jar devmate-client/target/devmate-client-*.jar &
curl -s -X POST localhost:8083/api/mcp/tools/search_code/call -H 'Content-Type: application/json' \
     -d '{"arguments":{"query":"Kafka"}}' | jq
```

## Acceptance test cases

42 cases in [docs/testing/M2-mcp-client-test-cases.md](../testing/M2-mcp-client-test-cases.md), automated by
`./scripts/check-mcp-client.sh`. The script runs the packaged jars: the real files MCP server, a misbehaving fake MCP
server (`scripts/support/fake_mcp.py`) and two DevMate instances, with no LLM. Result 2026-10-10: **42/42 PASS**.

Negative checks: with `DEVMATE_ADDRESS=0.0.0.0`, TC-37 fails. Without the read-only policy and schema check, TC-16,
TC-29 and TC-39 fail. With the attacker's domain in `DEVMATE_ALLOWED_HOSTS`, TC-42 fails. Regression: `check-client.sh`
89/89 and `check-files-mcp.sh` 56/56.

Found by the acceptance run and fixed:
- "First configured server wins" depended on property-source order: a command-line server shadowed `files`. It is
  now an explicit `priority`.
- An oversized answer was retried, doubling the wait. Oversized answers are no longer retried, and the message names
  `max-response-size`.
- Dropping a dead session logged an SDK stack trace (a graceful `DELETE` to a server that was gone). A broken session
  is now closed locally.

## Known limitations

- Streamable HTTP only (no stdio servers).
- Only read-only tools run. Others need the M13 approval flow.
- Only text content is kept. Image, audio and resource content become a placeholder line, and `structuredContent` is
  not used.
- Resources and prompts (the other MCP primitives) are not used yet.
- A server that changes its tools without `list_changed` is noticed on the next session, on a failed call
  (`Unknown tool`), or with `?refresh=true`.
- With the default 4 MB cap, the SDK needs about 4 s to reject an oversized one-line answer (it line-buffers first).
  A smaller per-server `max-response-size` makes this faster.
- `/api/mcp` has no authentication. It is protected by the loopback bind, JSON-only POSTs and the Host allowlist, and
  M13 adds more.
